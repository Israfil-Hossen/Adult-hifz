# Adult Hifz — how this app is built

Written for the person who opens this repo years from now with no memory of it —
possibly its own author. It explains what every file is, what language it is
written in, and what logic sits behind it.

Package `com.israfilhossen.hifz` · web version `1.0.4` · Android `versionCode 1`.

---

## 1. What the app does

A Quran memorisation companion for adults. It shows the mushaf page you are
memorising, tracks the daily cycle every hāfiz works through — **sabaq** (new
lesson), **sabaqi** (recent revision), **manzil** (older revision) — and decides
what comes back to you and when, based on how well you actually recalled it
rather than on a fixed calendar.

The user interface is Bengali by default, with English, Arabic, Urdu and Chinese
also complete.

---

## 2. The one architectural decision everything else follows from

**The whole app is one HTML file that runs offline, wrapped in a native shell.**

`hifz-1.0.8/index.html` is about 9,900 lines and contains the markup, the
stylesheet and the entire program. There is no build step, no bundler, no
framework, no npm dependency in the app itself. You can open that file in a
browser and the app runs.

Capacitor then wraps that same folder in an Android WebView so it can ship on
Play. The Android project is a shell — it contains almost no logic.

Why it was built this way, so you do not "modernise" it without knowing what you
would lose:

- **It must work with no network.** Users memorise on buses, in mosques, in
  places with bad data. Everything except audio and a few optional translations
  is on the device.
- **It must survive.** No framework version to chase, no dependency that stops
  resolving in 2031. Plain HTML, CSS and ES5-flavoured JavaScript will still open
  in whatever browser exists then.
- **The same code is a website and an app.** The PWA at a URL and the Play
  Store build are byte-identical, apart from the wrapper.

The cost is real and you should know it: one very large file, global functions,
no module system, no tests, and no type checking. Navigate it with the banner
comments (see §5), not by scrolling.

## 3. Languages used, and where

| Language | Where | Why there |
|---|---|---|
| **HTML** | `index.html` | The app's whole structure, in one document. |
| **CSS** | inside `index.html`, several `<style>` blocks | Theming, the mushaf page layout, three paper skins, responsive rules. No preprocessor. |
| **JavaScript (ES5-leaning, no build)** | inside `index.html`, `config.js`, `sw.js` | All app logic. Written deliberately conservatively — `var`, `function`, no imports — so it needs no transpiler. `async/await` is used where it earns its keep. |
| **JSON** | `hifz-1.0.8/data/**` | Mushaf page data, translations, word-by-word glosses, topic bands. About 30 MB total. |
| **PHP** | `hifz-1.0.8/sync.php` | The optional self-hosted backup endpoint. One file, ~80 lines, no framework, no database. |
| **Java** | `android/app/src/main/java/.../MainActivity.java` | Five meaningful lines. Installs the splash screen, then hands over to Capacitor. |
| **XML** | `android/app/src/main/res/**`, `AndroidManifest.xml` | Android resources: strings, colours, themes, permissions. |
| **Gradle (Groovy DSL)** | `android/*.gradle` | The Android build. Mostly generated by Capacitor. |
| **Node.js** | `brand/build.js` | Developer tooling only. Generates every icon and splash asset. Never ships. |

### `hifz-1.0.8/data/` — the Quran data

This is the bulk of the app's size, and none of it is code.

| Folder | Contents |
|---|---|
| `madani/`, `madani1421/` | Madani mushaf, 604 pages × 15 lines, 1405 and 1421 prints. Glyph-coded (QCF v1 / v2 fonts). |
| `indopak15/`, `indopak16/`, `ip13/`, `indopak13taj/` | Indo-Pak layouts: 610×15, 548×16, 849×13, 847×13. Rendered in Nastaʿlīq. |
| `tr/` | Full translations: Bengali (Abu Bakr Muhammad Zakaria), English (Daryabadi), Urdu (Bayan-ul-Quran), Chinese (Ma Jian). 6,236 ayahs each. |
| `wbw/bn.json` | Word-by-word Bengali gloss, ~3 MB. |
| `topics/bn.json`, `en.json` | Thematic section bands — where one subject on a page ends and the next begins. Editorial, so per-language. |
| `mut/ph.json` | Look-alike (mutashabihat) phrase data. |

Each mushaf folder holds `info.json` (page count, line count, font kind) plus
numbered chunk files `c0.json … cN.json`. A chunk holds many pages; the app
fetches only the chunk it needs. **Page data format**, per line:
`[wordId, "surah:ayah", glyph, isAyahEnd, plainArabic]`.

The glyph column is why there are two representations of the same word: the
mushaf page is drawn with a glyph-coded font where each code point *is* a
specific printed shape, preserving the exact line breaks of the physical
mushaf — which is the thing being memorised. The plain Arabic column is what
search, mutashabihat matching and the word bar use.

## 6. The data model

One object, one key, one blob.

```js
var KEY = "hifz-companion-v1";
```

Shape:

```js
{
  v: 1,
  settings: { lang, startDate, startPage, restDay, mushafId, reciter,
              manualLines, retention, paper, notifyAt, cloudCode, drive, … },
  known:   { pageNumber: true },      // memorised BEFORE using this app
  days:    { "2026-08-19": Day },     // one entry per calendar day
  weak:    { pageNumber: true },      // pages currently in trouble
  rev:     { pageNumber: RevCard },   // spaced-repetition state
  hl:      {}, bm: {},                // highlights, bookmarks
  drill:   { items, salat, sess },    // retrieval-practice history
  updatedAt: 1699999999999
}
```

A `Day`:

```js
{ sabaq: { pages:[], from:0, to:0, blocks:[false,false,false], done:false },
  gate: null,        // "pass" | "fail" — yesterday's lesson, tested today
  listen: false, sabaqi: [], salah: 0,
  manzil: { juz:0, done:false }, night: false,
  errors: 0, minutes: 0, note: "" }
```

**Persistence** goes through `Store`, which tries Capacitor's native storage
first, falls back to `localStorage`, and finally to an in-memory copy. `save()`
is debounced 220 ms and then fans out to local storage plus both sync paths.

`updatedAt` is the only conflict-resolution mechanism in the whole app. Last
write wins, and the server compares timestamps before overwriting.

## 7. The algorithms worth understanding

### 7.1 Revision engine — `revOf`, `revRecord`, `revDue`

Every memorised page carries a card:

```js
{ str: 0.5, ivl: 1, due: TODAY, reps: 0, lapses: 0, last: TODAY }
```

`revRecord(page, quality)` where quality is 0–1:

- **q ≥ 0.8** — clean recall. Strength `+0.12` (capped at 1), interval
  `× (1.6 + strength)`. Strong pages therefore spread out faster than weak ones.
- **q ≥ 0.5** — shaky. Strength `−0.05`, interval `× 0.8`.
- **q < 0.5** — failed. Strength `−0.25`, interval reset to 1 day, lapse counted.

Interval is clamped to 120 days. Below strength 0.4 a page is flagged weak; above
0.75 the flag clears. This is Ebbinghaus/Cepeda spacing, not SM-2 — simpler, and
tuned so that a page never disappears for longer than four months.

`revDue()` returns due pages **sorted weakest-first**, then applies one important
cap: pages in `known` (memorised before the app existed) are limited to
`settings.oldPerDay` per day, default 2. Without that cap someone who already
knew ten juz would be handed 200 pages on day one and quit.

### 7.2 The daily queue — `nextSlot`, `sabaqiQueue`, `manzilJuz`

- **`nextSlot()`** — where the new lesson starts. Walks the last completed sabaq;
  if it stopped mid-page, resume at the next line, otherwise move to the next page.
- **`sabaqiQueue()`** — up to 12 items. First the most recent distinct pages from
  the last week of completed lessons, then anything `revDue()` adds.
- **`manzilJuz()`** — the old-revision juz. Excludes anything already in the
  sabaqi queue, then rotates through the remaining juz on a weekly index. Returns
  0 (nothing) until at least 8 pages are memorised.
- **`streak()`** — a day counts if `dayScore()` ≥ 0.5, where the score is the
  fraction of six habits completed. Today is skipped rather than breaking the
  streak if nothing has been done yet.

### 7.3 Capacity — `capDays`, `capacity` — the most unusual piece here

The standard approach ramps new lines by the calendar: 5 lines in weeks 1–2,
8 in 3–4, 11 in 5–6, 15 after. It never looks at the reader.

This does instead. A day costs minutes on two things — new lines and revision
pages — so across many days:

```
minutes = a·lines + b·pages
```

with `a` and `b` unknown. Many days and two unknowns is a **least-squares fit**,
solved directly via the 2×2 normal equations (`Sll·Srr − Slr²` is the
determinant). It separates the cost of *learning* from the cost of *holding*,
without ever asking the user to time anything.

The day's budget `T` is the median of recent daily minutes. Solving
`T = L·a + revision·b` for `L` gives the lines this reader can actually take on.

The same equation yields something no linear forecast can see: revision alone
consumes the whole budget at `N = T·S̄/b` pages. **That is the ceiling** — the
most this person can hold at their current pace, in the time they really have.

### 7.4 Mutashabihat — `mutNorm` and friends

Adults confuse near-identical passages more than they forget them. Every page
already on the device is scanned for runs of **four or more identical words**
shared with the open page. Nothing is fetched. `mutNorm` strips diacritics,
tatweel and the alif/hamza and yā/alif-maqsūra variants before comparing, so
orthographic differences do not hide a genuine look-alike.

### 7.5 Retrieval practice — `EX` (test) and `DR` (drills)

Built on the finding that re-reading feels like learning while only retrieval
is: Karpicke & Roediger (2008), Rawson & Dunlosky (2011), Butler & Roediger
(2008). Three formats, all generated from page data already on the device:
reorder the pieces, fill the gap, choose the continuation. Delayed feedback,
a criterion of three flawless recalls, and an interval that follows how hard the
recall was. Wrong answers feed the day's error count and can mark a page weak —
the same number the revision engine reads.

## 8. Offline strategy — `sw.js`

Bump `const CACHE` on every release or users keep the old build.

Four rules, in order:

1. **Cross-origin, not a font** → do not touch it. Google login and Drive must
   never be cached.
2. **Fonts** → cache-first, then network, store on success.
3. **`/data/`** → cache-first, then network. Critically, this branch must never
   fall back to `index.html`; HTML arriving where JSON is expected breaks the page.
4. **App shell** → stale-while-revalidate. Serve the cache instantly, refresh in
   the background. On a cold cache, race the network against a **6-second
   timeout** and show whatever exists rather than a white screen.

That timeout is deliberate. It exists for users on heavily filtered or very slow
connections, who would otherwise stare at nothing.

## 9. Sync — two independent paths, both optional

### Code-based (`sync.php` + the `Cloud` object)

No accounts, no passwords. The user generates a code like
`ABC123-DEF456-GHJ789` (32-character alphabet with I, O, 0, 1 removed so it can
be read aloud and written down). That code is the only key.

Server side, in ~80 lines of PHP with no database:

- The code is validated against a **strict regex** before touching the
  filesystem. That regex is the path-traversal defence — nothing that fails it
  can become a filename.
- Storage is `sync-data/<sha256(code)>.json`, so reading the directory reveals
  no codes. The folder gets a `.htaccess` denying web access, plus an empty
  `index.html`.
- On POST, if the stored copy has a **newer `updatedAt`**, the server refuses to
  overwrite and returns its copy instead — the client adopts it.
- Writes go to a temp file then `rename()`, so two phones writing at once can
  never leave half a file.
- 8 MB body cap.

**PHP does not run on GitHub Pages.** This file needs real hosting.

### Google Drive (the `Sync` object)

Optional. Needs a Client ID in `config.js`. Backs the same JSON blob up to the
user's own Drive. If the ID is blank the button never appears.

## 10. Internationalisation

```js
var LANGS = ["bn", "en", "ar", "ur", "zh"];
var FALLBACK = "en";
```

Each pack is a nested object assigned to `window.HIFZ_LANG_xx`. `deepFill`
merges the active pack over English, **key by key, recursively** — so a
half-finished translation still produces a working app, with untranslated
strings appearing in English rather than as blanks or crashes.

`fmt(str, ...)` handles `{0}` placeholders. `n(x)` converts digits to the
locale's numerals — Bengali and Urdu do not use Western digits.

To add a language: copy the English pack, translate the values only, add the
code to `LANGS`. Never translate keys, `{0}` markers, or code.

Urdu and Arabic are RTL and the CSS handles direction; the mushaf page is always
RTL regardless of interface language.

## 11. Build, release, and the traps

### Commands

```bash
npx cap sync android      # copy hifz-1.0.8/ into the Android project
npm run apk               # debug APK
npm run bundle            # release AAB (needs signing config — not set up yet)
node brand/build.js       # regenerate every icon and splash asset
```

**Editing `hifz-1.0.8/` changes nothing in the Android build until you run
`cap sync`.** Gradle only ever sees the copy at
`android/app/src/main/assets/public`. This will confuse you at least once.

### Trap 1 — the JDK

Gradle 8.14.3 (pinned by Capacitor 8) supports Java **up to 24**. Any newer JDK
fails with `Unsupported class file major version 69`. `android/gradle.properties`
pins `org.gradle.java.home` to a JDK 21 install.

**Android Studio ignores that line** and uses its own setting. Set
*Settings → Build Tools → Gradle → Gradle JDK* to the same JDK 21, or Studio
will fail while the command line succeeds.

### Trap 2 — the splash screen

`Theme.SplashScreen` reads `windowSplashScreenBackground` and
`windowSplashScreenAnimatedIcon`. It **ignores `android:background`** — that is a
View attribute and a window theme does nothing with it. Setting it looks
plausible and silently does nothing.

Also: since Android 12 the system splash is **one background colour and one
centred icon, masked to a circle**. Full-screen splash images are gone from the
platform. That is why the branded lockup with the wordmark is painted by the web
app on its first frame (`#brandsplash` in `index.html`) rather than by Android.

The icon canvas is 288dp with only the inner **192dp** safe, so the mark is
generated at 176/288.

### Trap 3 — adaptive icon geometry

The foreground layer must be the mark alone **on transparency** — never a filled
rectangle, or the background layer is hidden and the launcher's parallax shows a
sliding block. Only the centre **66%** of the canvas is guaranteed visible, so
`brand/build.js` draws the mark at 0.58 of the canvas for the adaptive
foreground and 0.68 for unmasked icons.

### Trap 4 — dead splash assets

`npx capacitor-assets generate` emits 26 full-screen `splash.png` files for the
legacy splash system. Nothing references them any more. They add ~2 MB to the
APK and are deleted after each generate run.

### 11.5 Release signing, and why Play Protect flags debug builds

A debug APK is signed with a keystore Android generates automatically, whose
identity is literally `CN=Android Debug, O=Android, C=US` — shared by every
developer on earth — and it carries `android:debuggable="true"`, which lets any
process on the phone attach a debugger to it.

Sideload that and **Google Play Protect will disable it as "harmful"**, with the
wording *"This app is fake. It tries to take over your device or steal your
data."* That is a heuristic about an unattributable, debuggable, sideloaded app
requesting the microphone — not a finding about this code. It is also not
entirely wrong: a debuggable build genuinely is less safe.

The cure is a release build signed with your own key.

1. Create the keystore once, outside the repo, and never lose it — Google will
   not accept a different key for this package afterwards:

   ```
   keytool -genkeypair -v -keystore adult-hifz.jks -keyalg RSA            -keysize 2048 -validity 10000 -alias adulthifz
   ```

2. Copy `android/keystore.properties.example` to `android/keystore.properties`
   and fill it in. Both `keystore.properties` and `*.jks` are gitignored.

3. `npm run bundle` for the Play AAB, or `gradlew assembleRelease` for an APK.

`minifyEnabled` is deliberately **off** on release. R8 on a Capacitor WebView app
needs keep-rules this project has not written, and the size win is small next to
30 MB of Quran data.

## 12. The brand pipeline — `brand/build.js`

Node + `sharp`. Not part of the app; it only produces assets.

The single source of truth is the word **حفظ** set in **Alkalami** (SIL Open
Font License — `brand/fonts/Alkalami-OFL.txt`). Text is rendered through
Pango so Arabic shaping and letter-joining are correct, auto-fitted to a
2400×1400 box for resolution, trimmed to its ink bounds, then scaled and
composited into every asset.

Change the font or the word in one place and run `node brand/build.js` — all 20
assets regenerate consistently. Aref Ruqaa is also in `brand/fonts/` as an
alternative; switching is two lines.

Outputs: `assets/icon*.png`, `hifz-1.0.8/icon-*.png`, both splash lockups, and
the ten `ic_splash.png` density variants.

## 13. Things that are not done

Recorded honestly so you do not go looking for them.

- **No keystore in the repo, by design.** `signingConfigs` is wired up, but the
  key itself is not here and never should be. Without `android/keystore.properties`
  a release build produces `app-release-unsigned.apk` rather than failing. See §11.5.
- **No tests of any kind.** The two files in `androidTest/` and `test/` are
  Capacitor's untouched stubs.
- **No `@capacitor/splash-screen` plugin.** `capacitor.plugins.json` is empty;
  the splash is handled by the theme plus the web overlay instead.
- **The root `.zip` and `.bz2` files** are research sources used to build
  `data/`. They are not shipped and not referenced by any code.
- **Google Drive sync is untested** in the packaged Android build; it was built
  for the PWA.
- **The Urdu and Chinese packs** carry notes from their authors asking for a
  native-speaker review before release. As far as this document knows, that has
  not happened.
